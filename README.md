## Задание 
### Вариант 9 - Редактор подземелья с NPC: Эльф, Дракон, Друид

#### Требования к программе:
- Реализовать редактор подземелья для RPG игры Balagur Fate 3
- Поддержка размещения NPC в квадрате 0<=x<=500, 0<=y<=500 метров
- У каждого NPC должно быть уникальное имя и координаты
- Возможность сохранения/загрузки объектов в файл
- Реализация боевого режима с определенной дальностью атаки
- Правила боя: Дракон → Эльф, Эльф → Друид, Друид → Дракон

#### Обязательные паттерны:
1. **Factory** - для создания NPC и загрузки из файла
2. **Visitor** - для проведения цикла сражений
3. **Observer** - для логирования событий боя в файл и на экран

## Особенности реализации

### 1. Паттерн Factory
#### Иерархия создания объектов:
- **`INPCCreator`** - абстрактный интерфейс создателя NPC
- **`NPCFactory`** - основная фабрика, управляющая создателями
- **Конкретные создатели**: `ElfCreator`, `DragonCreator`, `DruidCreator`

#### Функциональность:
- Создание NPC по типу и параметрам
- Загрузка NPC из файла с обработкой ошибок
- Сохранение NPC в файл (только живые персонажи)
- Валидация координат через класс Point

### 2. Паттерн Visitor
#### Реализация двойной диспетчеризации:
- **`Visitor`** - интерфейс посетителя
- **`BattleVisitor`** - боевой посетитель для обработки сражений

#### Логика боя:
```cpp
// Правила атаки:
- Elf атакует Druid ✓
- Dragon атакует Elf ✓  
- Druid атакует Dragon ✓
// Остальные комбинации - бой не происходит
```

#### Особенности:
- Проверка состояния NPC (жив/мертв) перед боем
- Интеграция с системой Observer для логирования
- Поддержка определения победителя и проигравшего

### 3. Паттерн Observer
#### Система наблюдения за боями:
- **`Observer`** - интерфейс наблюдателя
- **`Subject`** - интерфейс субъекта для управления наблюдателями
- **`BattleLogger`** - менеджер наблюдателей боя

#### Конкретные наблюдатели:
- **`ConsoleLogger`** - вывод в стандартный поток
- **`FileLogger`** - запись в файл "log.txt"

#### Функциональность:
- Автоматическое уведомление всех наблюдателей о событиях
- Гибкая система подписки/отписки
- Разделение ответственности между разными типами логгеров

### 4. Класс Point
- Валидация координат (0-500)
- Исключения `std::out_of_range` при невалидных значениях
- Перегрузка операторов для удобства использования

### 5. Иерархия NPC
#### Базовый класс `INPC`:
- Виртуальные методы: `getName()`, `getType()`, `getPosition()`, `isAlive()`
- Метод `accept()` для поддержки паттерна Visitor
- Состояние: живой/мертвый

#### Конкретные NPC:
- **`Elf`** - атакует друидов
- **`Dragon`** - атакует эльфов  
- **`Druid`** - атакует драконов

## Выводы
В ходе лабораторной работы были успешно освоены и применены три ключевых паттерна проектирования:

1. **Factory** - позволил создать гибкую систему создания NPC с возможностью расширения новыми типами персонажей
2. **Visitor** - обеспечил реализацию сложной логики боев через двойную диспетчеризацию, позволяя добавлять новые операции без изменения классов NPC
3. **Observer** - создал эффективную систему уведомлений о событиях боя с поддержкой multiple логгеров

**Преимущества реализованного подхода:**
- Высокая связность within модулей и низкая связность between модулей
- Легкость добавления новых типов NPC и правил боя
- Гибкая система логирования с возможностью добавления новых наблюдателей
- Корректная обработка ошибок и пограничных случаев

Работа продемонстрировала мощь объектно-ориентированного подхода и паттернов проектирования для создания сложных, но поддерживаемых систем. Все компоненты успешно интегрированы и протестированы, что подтверждает корректность реализации.
